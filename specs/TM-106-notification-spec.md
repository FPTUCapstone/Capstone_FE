# TM-106 / UC-59 Operator In-App Notification (gap closure)

Authorized scope: add the missing FE in-app notification UI for Tour Operators, closing the gap found during TM-106 E2E UAT (2026-11-24): Backend PR #200 (Capstone_BE, merged `7f682b5f`) already writes approval notices into the existing shared `Notification` entity/table and exposes them via `NotificationsController` (`GET /api/v1/notifications`, `POST /api/v1/notifications/{id}/read`), but no FE surface reads this API — Operators see nothing after a tour is approved. Source: TM-106 UAT report `_handover/tasks/TM-106/working/E2E_UAT_report_2026-11-24.md`, Case 1 Step 5. Backend is out of scope; this is FE-only.

- Scope is the Tour Operator workspace (`src/features/operator/...`, `PartnerHeader`/`PartnerWorkspaceLayout`), not the Hotel Service Provider workspace (`ProviderTopbar`) or Admin/Staff — no change to other roles.
- API contract (existing, do not modify): `GET /api/v1/notifications?unreadOnly=&limit=&beforeId=` returns `{ items: Array<{ id, type, title, body, relatedEntityType, relatedEntityId, createdAtUtc, isRead }>, nextBeforeId: number|null }`; `POST /api/v1/notifications/{id}/read` returns 204. Both require the operator bearer token (401 if missing/expired) and only return the authenticated user's own `Channel = InApp` notifications — no cross-user data.
- No BE SignalR hub exists for notifications (confirmed by code search on `origin/develop`). Do not add a realtime hub dependency; use polling only, following the `useWeatherSafetyRealtime` polling-fallback interval (30s) as precedent, to avoid repeating the UAT-observed SignalR 404 noise from an unrelated hub.
- Add a bell icon with an unread-count badge to `PartnerHeader` (the real header rendered for all `/partner/*` pages, confirmed empty of any notification affordance today). On click, show a dropdown/panel listing recent notifications (title, body, relative time, read/unread state). Clicking an item calls mark-read and, when `relatedEntityType`/`relatedEntityId` resolve to a known operator route (tour), navigates there.
- Badge count must only count unread (`unreadOnly=true` or client-side filter); must not break existing `PartnerHeader` tests (breadcrumbs, mobile toggle, demo badge, operator name) — those props/behaviors are unchanged, notification state is additive.
- Follow existing feature module conventions under `src/features/operator/weather-safety/` (api client class extending an `Error` subtype, `handleFailure` for 401/403/400, parser with `isRecord` guard, polling hook with debounce/cleanup) — do not invent a new HTTP wrapper or state library.
- No new page/route is required for this gap closure (no `/notifications` full page) — a header dropdown satisfies the UC-59 acceptance criterion that the Operator is informed. A full inbox page can be a separate future task if requested.
- Technical limits: badge caps at reasonable display (e.g., "9+") if count is large; dropdown shows a bounded page (reuse API `limit`, default consistent with BE default of 20) with no infinite scroll required for this gap closure.
- Reuse existing design tokens/classes from `PartnerHeader`/`PartnerSidebar` (no new color system). No redesign of unrelated header elements (breadcrumbs, demo badge, operator chip, logout).

Verification: unit tests for the new API client (mocked fetch, success/401/403/400 paths), the polling hook (interval firing, cleanup on unmount, error swallow), and the updated `PartnerHeader` (badge renders count, dropdown opens/closes, mark-read called on item click) — existing `PartnerHeader.test.tsx` cases must keep passing unmodified. Then `npm run lint && npm run typecheck && npm run build`. No commit, push, PR or merge has been requested for this task; work stays local pending developer review.
